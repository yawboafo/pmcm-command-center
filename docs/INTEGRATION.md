# Integration guide — connecting real devices, cameras and order systems

The command center is built so that every simulated source can be replaced by a real one
without touching UI or business logic. External systems are translated at the edge into the
canonical contracts in `src/lib/integration/contracts.ts`; everything downstream (food-safety
limits, alert delays, the 3D twin, panels, analytics) consumes only those shapes.

**Provenance rule:** every value carries `source: "live" | "virtual" | "simulated"` and the UI
shows a LIVE, SIM DEVICE or SIMULATED badge:

| Source | Meaning | Badge |
|---|---|---|
| `live` | A physical device or system through the integration pipeline | LIVE (green) |
| `virtual` | Simulated hardware (`npm run hardware:sim`, `npm run camera:sim`) through the **same** pipeline | SIM DEVICE / SIM CAMERA (fuchsia) |
| `simulated` | Generated by the in-browser simulation | SIMULATED (amber) |

The server decides `origin: "physical" | "virtual"` from the registry the sender is bound in
(`devices.json` vs `devices.virtual.json`), never from the message, so simulated hardware can
never display as LIVE. A device-fed sensor (live or virtual) replaces the simulated value for that
sensor only, and its simulated history is discarded so charts never mix the two. Safety and alert
logic is source-agnostic: the same limits and delays apply to all three.

The first pipeline event (reading or order, from physical or simulated hardware) switches the
console from the demo clock to the real wall clock at 1× and restarts open branch simulations on
that timeline, so pipeline and demo timelines never mix; the notification says which kind
arrived ("Live data received…" or "Simulated hardware connected — clock switched to real time"). A newly opened console only replays the last 5 minutes of buffered
events, so stale data never makes the console look live; a reconnecting console resumes from
its `Last-Event-ID` and gets everything still buffered.

## Device telemetry contract (`TelemetryMessage`, v1)

```json
{
  "v": 1,
  "messageId": "6f1c0e0a-5c1d-4d0f-9a43-2f7d1b9c8e11",
  "deviceId": "acc-eastlegon-coldroom-01",
  "ts": "2026-11-03T12:15:30Z",
  "readings": [{ "metric": "temperature_c", "value": 3.4 }],
  "battery_pct": 87,
  "rssi_dbm": -71,
  "firmware": "2.4.1"
}
```

- `messageId` must be unique per message; retries with the same id are acknowledged as
  duplicates (HTTP 200) and not applied twice.
- `ts` is the device clock. Devices and gateways **must be NTP-synchronised**; messages
  timestamped more than 2 minutes in the future are rejected (`clock_skew`).
- Metrics and units are fixed: `temperature_c`, `probe_temperature_c`, `oil_quality_pct`
  (100 = fresh oil), `door_open` (1/0), `power_w`, `humidity_pct`, `status` (1 OK / 0 fault).
  Multi-probe devices add `channel` per reading.

### Signing (HTTPS)

| Header | Value |
|---|---|
| `x-pmcm-device` | device id |
| `x-pmcm-timestamp` | Unix epoch milliseconds at signing |
| `x-pmcm-signature` | hex `HMAC-SHA256(secret, "${timestamp}.${rawBody}")` |

Requests outside a ±5 minute window are rejected, which blocks replay of captured requests.
Responses: `202` accepted, `200` duplicate, `400` schema / clock skew, `401` unknown device,
bad signature or stale timestamp, `413` too large, `422` metric not bound for this device.

Per-device secrets live in the server environment as `DEVICE_KEYS='{"<deviceId>":"<secret ≥16 chars>"}'`
in the prototype. In production use a secrets manager and per-device X.509 certificates (mTLS).

### MQTT

Gateways that prefer MQTT publish the same JSON to `pmcm/v1/{branchCode}/{deviceId}/telemetry`
(QoS 1). In production an MQTT → ingestion bridge verifies the device certificate, then hands
the message to the same validation and binding code as the HTTPS route.

### Binding devices to the floor plan (`src/data/devices.json`)

```json
{ "deviceId": "acc-eastlegon-coldroom-01", "branchId": "branch-015", "equipmentId": "walk-in-cold-1",
  "metric": "temperature_c", "calibrationOffset": -0.2, "expectedIntervalSec": 60,
  "model": "…", "installedAt": "2026-12-01", "lastCalibratedAt": "2026-12-01" }
```

- Bind to `equipmentId` (stable across floor-plan edits) wherever possible. Use `sensorCode`
  (for example `SNS-034`) only for sensors not attached to equipment, such as a QC food probe;
  sensor codes can change when the editor re-places sensors.
- `calibrationOffset` is added to every raw value; take it from the latest calibration
  certificate and update it at each recalibration.
- A device is shown offline after 3 × `expectedIntervalSec` without data, and the twin raises a
  "sensor connectivity lost" alert for that sensor.
- Readings for equipment that does not exist in the branch floor plan are counted as
  "unmatched" on Settings → Integrations; fix the binding or the floor plan.

### Bench test

```bash
npx tsx scripts/device-sim.ts --device bench-coldroom-01 --value 3.2 --drift 0.5 --interval 2
```

`--drift` raises the value each reading to imitate a failing compressor; the twin shows the
LIVE reading, then opens a LIVE alert after the configured delay.

## POS / ordering webhook (`PosOrderEvent`, v1)

```json
{
  "v": 1,
  "idempotencyKey": "b1e0c9f4-…",
  "branchId": "branch-015",
  "externalRef": "CB-778812",
  "channel": "chris-b-app",
  "fulfilment": "delivery",
  "status": "RECEIVED",
  "lines": [{ "menuId": "pz-chicken-l", "qty": 1, "unitPriceGhs": 150 }],
  "ts": "2026-11-03T12:15:30Z"
}
```

- Signed like devices, with `x-pmcm-source` (sender id, e.g. `chris-b`, `pos-eastlegon`) in place
  of `x-pmcm-device`, and the shared secret `POS_WEBHOOK_SECRET` (≥16 characters).
- Send one event per status change: `RECEIVED`, `ACCEPTED`, `READY`, `COMPLETED`, `CANCELLED`,
  `REFUNDED`. Events are idempotent on (`x-pmcm-source`, `idempotencyKey`), so retries are safe.
- `branchId` and `menuId` must already be mapped to command-center ids; unknown ids are refused
  with `422` rather than guessed. Keep the mapping table in the integration service.
- Prices from the source system are authoritative and replace catalogue prices on that order.
- Live orders appear with a LIVE badge. **Kitchen progress is still simulated** until a kitchen
  display (KDS) or station-level system is connected; the order inspector says so.

Bench test: `npx tsx scripts/pos-sim.ts --branch branch-015 [--final CANCELLED]`.

## Cameras

Virtual cameras are viewpoints in the 3D model and are always labelled SIMULATED VIEW. Physical
cameras are a separate path:

1. IP cameras with ONVIF Profile S and RTSP (H.264 recommended for browser compatibility).
2. A media gateway in the branch or a regional site — MediaMTX is the reference: RTSP in,
   WebRTC (WHEP) and HLS out. Set `CAMERA_GATEWAY_URL` on the server.
3. Register each camera in `devices.json → cameras` with its authorisation (`approvedBy`,
   `approvedAt`, `purpose`, `privacyNoticeUrl`, `retentionDays`), `streamPath` on the gateway,
   and optionally `virtualCameraId` when it is mounted at the pose of a virtual camera.
4. The browser posts its SDP offer to `/api/cameras/{cameraId}/whep`; the server checks that
   the camera is registered and enabled and forwards it to the gateway. Camera addresses and
   credentials never reach the browser.
5. Live video plays only in the labelled LIVE CAMERA player (Settings → Integrations, or the
   "LIVE FEED" button on a matching tile in the twin's camera grid). It is never composited
   into the 3D simulation.

Not yet done: the proxy does not forward the WHEP session `Location` header, so sessions are
closed by the gateway's timeout rather than an explicit `DELETE`; HLS playback is not
implemented. Set `NEXT_PUBLIC_STUN_URL` only if consoles reach the gateway across NAT.

Cameras with `protocol: "mjpeg"` (multipart/x-mixed-replace) are relayed by
`GET /api/cameras/{id}/mjpeg` after the same registry/enabled checks, and play in an `<img>`
player. Simulated cameras (`virtual: true`) need no authorisation block (nobody is filmed) and are
labelled SIM CAMERA; they may use `VIRTUAL_CAMERA_GATEWAY_URL` so they can run next to a real
MediaMTX gateway on `CAMERA_GATEWAY_URL`.

## Simulated hardware fleet

Real sensors, POS and cameras are not installed yet, so the whole hardware fleet is simulated
**through the real integration pipeline**: signed HTTP to the same ingestion routes, the same hub
(bindings, calibration, de-duplication, replay buffer), the same SSE stream and the same engine
ingest code as physical hardware. Only the provenance differs (SIM DEVICE).

### Registry (`src/data/devices.virtual.json`)

Generated by `npm run generate:fleet` (`scripts/generate-fleet.ts`) from the floor plans of the
three demo branches. Every entry has `"virtual": true`.

| Branch (plan) | Devices | POS sources | Cameras |
|---|---|---|---|
| East Legon `branch-015` (Model C) | 27 | 3 (2 counter POS + online-ordering feed) | 6 |
| Spintex `branch-033` (Model B) | 14 | 2 | — |
| KNUST `branch-046` (Model A) | 14 | 2 | — |

Devices: air-temperature probes on every fridge, freezer, walk-in, drinks fridge, make-line,
hot-holding cabinet, heated QC pass and rice warmer (LoRaWAN for walk-ins and upright cabinets,
Wi-Fi elsewhere); a door contact on each walk-in; inline oil-quality (TPM) sensors and controller
gateways (`status`) on fryers; controller gateways on ovens; Bluetooth QC food probes bound by
sensor code. Each has a model description, reporting interval (60–300 s; probes up to 30 min),
calibration offset, install/calibration dates and a `hardware` block (thermal, oil, radio,
battery) that only the simulator reads. The hub loads both registries.

Keys: instead of one secret per device, each virtual device, terminal and the simulator heartbeat
signs with `HMAC-SHA256(VIRTUAL_FLEET_SECRET, id)` (`src/lib/integration/fleet.ts`). A physical
`DEVICE_KEYS` entry never authenticates a virtual id, and a virtual terminal cannot sign with
`POS_WEBHOOK_SECRET`. Set `VIRTUAL_FLEET_SECRET` (≥ 32 characters) in `.env.local` and restart.

### Hardware simulator (`npm run hardware:sim`)

One process runs the selected branches' devices and POS terminals:

- **Thermal models**: thermostat-driven compressor/heater duty cycles with hysteresis, defrost
  cycles on freezers and walk-ins, door openings that follow the demand curve (more during lunch
  and dinner peaks) and pull warm air in.
- **Fryer oil**: quality falls with each cooking load and slowly while hot; the crew changes the
  oil in a quiet spell below ~40 % or as soon as possible below the change point.
- **Radio and power**: battery drain over the nominal life, RSSI noise (weaker in walk-ins),
  packet loss with retries of the same `messageId`, lost acks that resend an accepted message
  (exercises de-duplication), device offline gaps and branch LoRaWAN-gateway outages with
  buffered catch-up (original timestamps, oldest first), and occasional device clock skew (a few
  minutes ahead → `400 clock_skew` → NTP resync → timestamps corrected and resent).
- **Faults**: rare spontaneous ones (sensor drift, stuck readings, compressor/heater failure, door
  left ajar, controller trips) that a "technician" repairs after a while, plus injected ones.
- **POS**: orders at the demand curve from the real catalogue (`MENU`, catalogue prices), signed
  `PosOrderEvent`s `RECEIVED → ACCEPTED → READY → COMPLETED` (some `CANCELLED`), store-and-forward
  during short terminal outages, occasional webhook retries.
- **Heartbeat**: every 20 s to `POST /api/ingest/simulator` with the active simulated faults, shown
  in Settings → Integrations.

```bash
npm run hardware:sim -- [--url http://localhost:3000] [--branches eastlegon,spintex,knust]
    [--speed 10] [--chaos 1] [--fault <deviceId>:<kind>]... [--no-pos] [--no-devices] [--list] [--quiet]
```

`--speed` accelerates physics and order flow; timestamps stay real (the server rejects
future-dated readings). `--chaos` scales the random fault/outage rates (0 disables them). Fault
kinds: `compressor`, `door-ajar`, `drift`, `stuck` (cold probes); `heater`, `drift`, `stuck`
(hot probes); `oil-overdue`, `drift` (oil); `trip` (controllers); `undercook` (QC probes); and
`offline`, `battery`, `skew`, `dupes` on any device. Example: a failed hot-holding heater raises a
SIM DEVICE food-safety alert about 2 minutes (at `--speed 10`) plus the 5-minute alert delay later:

```bash
npm run hardware:sim -- --speed 10 --fault v-eastlegon-hot-holding-1-temp:heater
```

### Simulated cameras (`npm run camera:sim`)

`scripts/camera-sim.ts` serves an MJPEG stream per simulated camera on `127.0.0.1:8090`
(ffmpeg `testsrc2` with an overlay: camera name, branch, running GMT timestamp and a "SIMULATED
CAMERA" banner). The overlay is drawn by the script and piped to ffmpeg, so ffmpeg builds without
`drawtext` work. ffmpeg runs only while someone watches. The console reaches it only through
`/api/cameras/{id}/mjpeg`; set `VIRTUAL_CAMERA_GATEWAY_URL=http://127.0.0.1:8090` (or
`CAMERA_GATEWAY_URL`). The six East Legon cameras are registered at the pose of virtual cameras
`cam-1`, `cam-4`, `cam-8`, `cam-12`, `cam-17` and `cam-20`; their tiles in the Virtual Cameras grid
show a **SIM CAMERA** button.

### What it does not simulate

Kitchen progress of pipeline orders is still the in-browser simulation (no KDS). QC food probes
are only used while a branch is open, so a branch that closes overnight (Spintex) reports its
probe offline after 3 × 30 min — a real deployment needs a closed-hours schedule for alerts.
Physics is plausible, not calibrated against the branches' actual equipment.

## Recommended hardware (to validate with the operations team)

| Need | Option | Notes |
|---|---|---|
| Fridge / freezer / walk-in air temperature | Wireless probes, LoRaWAN (with a branch gateway) or Wi-Fi | LoRaWAN gets through cold-room walls better; choose probes rated for −40 °C in freezers |
| Hot-holding cabinets | Wired or wireless probe rated to ≥ 120 °C | |
| Cooked-chicken core temperature | Bluetooth food probe with a tablet app at QC | Report as `probe_temperature_c` bound by `sensorCode` |
| Fryer oil quality | Inline total-polar-material sensor or handheld TPM meter | Report as `oil_quality_pct` |
| Door open / power | Reed switch; CT clamp energy monitor | Optional; `door_open`, `power_w` |
| Cameras | ONVIF/RTSP IP cameras + MediaMTX gateway | See Cameras |

Devices should buffer readings locally while offline and send them with their original `ts`
when the link returns (new `messageId` per reading). Calibrate probes against a reference
thermometer at installation and at a fixed interval; record each certificate's offset.

## Production path

```
devices ──MQTT/mTLS──► broker ─┐
gateways ──HTTPS+HMAC─────────┤► ingestion service (validate, bind, calibrate, de-duplicate)
POS / Chris B ──webhook───────┘          │
                                         ▼
                           Redis Streams or Kafka  ──► alert/rules service (same limits as today)
                                         │
                                         ▼
                           TimescaleDB (readings, orders, audit) ──► NestJS WebSocket gateway ──► consoles
```

- Replace the in-process hub with the stream; keep `contracts.ts` as the shared schema.
- Move the bindings and camera registry from `devices.json` into Postgres (schema sketch in
  `prisma/schema.prisma`), editable by administrators with audit logging.
- Replace `CONSOLE_ACCESS_TOKEN` with authenticated sessions and branch-scoped RBAC enforced on
  the server, including on the live stream and camera routes.
- Run alerting server-side so alerts fire and notify staff even when no console is open.

## Staff location badges (RTLS)

Staff can wear location badges read by an RTLS (real-time location system): **UWB** badges
(≈10–30 cm, needs ceiling anchors every ~8–12 m and a site survey) or **BLE** badges
(≈1–3 m, cheaper beacons/gateways). The RTLS engine — or its gateway — posts one signed fix per
badge to `POST /api/ingest/location`:

```json
{ "v": 1, "messageId": "…", "tagId": "uwb-eastlegon-0007", "ts": "2026-11-03T12:15:30Z",
  "x": 7.42, "y": 3.10, "accuracy_m": 0.21, "battery_pct": 81, "anchors": 5 }
```

- Signed like device telemetry (`x-pmcm-device` = tag id). Physical tags (or the RTLS gateway)
  use `DEVICE_KEYS`; simulated tags derive their key from `VIRTUAL_FLEET_SECRET`.
- `x`/`y` are in the RTLS **site frame**. Each binding (`wearables` in `src/data/devices*.json`)
  carries the calibration to the floor plan (`offsetX`, `offsetZ`, `rotationDeg`, `scale`) —
  measure it once per site by surveying two or three known points (e.g. door centres).
- A badge is bound to a staff member (`staffId`; production: the HR / rota employee id).
- From the first fix that person is **shown** where the badge says. What they are doing is still
  simulated (no kitchen display system is connected), so their simulated work continues in the
  background and the kitchen keeps producing. After 30 s without fixes the badge shows
  **signal lost** (last known position); after 10 minutes the person is simulated again.
- The console shows badge positions with their provenance (LIVE, or SIM DEVICE for the
  simulated badges), the accuracy as a disc, and the virtual camera with the best view.

**Privacy (required before go-live).** Staff location is personal data under the Data
Protection Act, 2012 (Act 843) and an employment matter under the Labour Act, 2003 (Act 651):
- Track only on shift and on the premises; badges are left at the branch, never taken home.
- Give staff a written notice of what is tracked, why (food-safety zoning, response to alerts,
  workload balancing) and for how long data is kept; record the notice version and date in the
  binding's `consent` field. Consult staff representatives and counsel first.
- Named positions are limited to roles with `view:staff-location` (managers, kitchen
  supervisors); other roles see anonymised staff. Enforce this server-side in production and
  keep an access log.
- Do not use positions for individual performance scoring without separate review. Keep raw
  position history short (e.g. 30 days) unless an incident requires otherwise.

Simulated badges: `npm run wearables:sim` (all three demo branches; `--branches branch-015`,
`--interval`, `--speed`, `--dropout`). Bindings are generated by `npm run generate:fleet`.

## Privacy and legal

- Ghana's Data Protection Act, 2012 (Act 843) applies to CCTV footage of staff and customers and
  to customer order data. Confirm registration duties with the Data Protection Commission and
  the lawful basis for each purpose with counsel before connecting cameras or order data.
- Display CCTV signage at each branch, publish the privacy notice referenced in each camera's
  authorisation, set and enforce retention periods, and restrict live viewing to authorised
  roles with an audit log.
- Do not use cameras for purposes beyond the recorded authorisation (for example, staff
  performance monitoring) without separate review.
