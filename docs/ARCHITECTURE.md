### One floor plan, many consumers

`src/lib/floorplan/types.ts` defines the schema (schemaVersion 1). Templates A/B/C are generated by
`scripts/generate-floorplans.ts` into `src/data/floorplans/*.json`. Walls are **derived** from
room rectangles + `openings` + doors/windows, so resizing a room in the editor re-cuts the walls.
Cameras, sensors and reference paths are derived too, and can then be edited by hand.

The same JSON drives: the 2D architectural view and editor, the procedural 3D restaurant, the
virtual camera network, the kitchen workflow engine (workstations + stand points), food-safety
sensor placement and the navigation grid used for path-finding and circulation validation.
A branch uses a template copy until an administrator saves a custom layout (versioned, with rollback).

### Simulation engine (`src/lib/sim/engine.ts`)

Deterministic (seeded PRNG, fixed 0.25 s steps), event-driven, one instance per opened branch:

- **Demand** — Poisson arrivals × lunch/dinner demand curve; walk-in vs remote channels.
- **Orders** — full lifecycle RECEIVED → … → COMPLETED, plus CANCELLED/REFUNDED, SLA delay flags.
- **Kitchen** — each menu item expands into production units with staged tasks
  (pizza: make-line → conveyor oven → cut/QC; chicken: picked from hot-holding, which fryers
  replenish in batches with a core-temperature check; rice: portioned from a batch-cooked warmer).
  A scheduler assigns tasks to staff by skill, distance and station capacity.
- **Agents** — staff, customers (queue → order → wait → collect → sit/leave), riders; A* on the
  occupancy grid so nobody walks through walls or equipment.
- **Equipment & safety** — temperature models with injectable faults, configurable thresholds,
  alert lifecycle (open → acknowledged → resolved; resolution requires a corrective action **and**
  an in-range reading), cleaning checklists, cook-temperature verification log, oil quality.
- **Inventory** — recipe-based deduction on completion with an idempotent ledger key
  (`order:<id>`), batch production consumption, low-stock/expiry status, auto-replenishment.

Tests: `npx vitest run` (determinism, flow-to-completion on all three layouts, ledger dedup,
alert rules, demo order routing, reachability of every workstation).

## Target production architecture (next phases)

```
 POS / Chris B / call centre / partners ──► Order Service ─┐
 IoT gateway (temperature, equipment)  ──► Telemetry Svc ──┤
                                                           ▼
                                   Event bus (Redis Streams → Kafka at scale)
                       ┌──────────────┬───────────────┬──────────────┬─────────────┐
                       ▼              ▼               ▼              ▼             ▼
                 Kitchen Svc   Inventory Svc   Safety Svc     Delivery Svc   Analytics
                       └──────────────┴───────┬───────┴──────────────┘
                                              ▼
                               PostgreSQL + PostGIS (prisma/schema.prisma)
                                              ▼
                                   WebSocket gateway (NestJS)
                                              ▼
                        Browser: same UI, `LiveDataSource` instead of simulation
```

- **Server-authoritative state** for real orders, inventory and safety; the UI only visualises.
- **Events** carry ids, timestamps and idempotency keys; consumers deduplicate; clients resume
  from the last acknowledged sequence after a dropped connection.
- **Separation of real and simulated data** — `DataSource` column on every operational table;
  simulation events live in `SimulationSession`/`SimulationEvent` only.
- **Security** — OIDC login, RBAC with org/region/branch-scoped grants (`UserRole`), enforced in the
  API (the prototype's client checks only shape the UI); audit log for every mutation; TLS; rate
  limiting (Redis); schema validation at every boundary; secrets in a secrets manager.
- **CCTV** — optional, per-branch, explicitly authorised, behind a streaming gateway
  (RTSP → WebRTC/HLS) and shown in a separate labelled player. Never blended with the simulation.
- **AI assistant** — keep the tool-use pattern; tools call authorised, branch-scoped APIs with the
  user's token instead of reading the in-browser simulation.

## Performance notes

- Only the entered branch's 3D scene is mounted (TwinView is keyed by branch and lazy-loaded).
- Full simulations run only for opened branches; the other branches use an O(1) seeded model.
- Panels re-render at ≈4 Hz; the 3D layer reads engine state inside `useFrame` without React updates.
- Graphics presets (high / balanced / low) control shadows and pixel ratio.
